# Curriculum Designer — database schema

Task 2. The Pydantic models in `models/` as database tables, plus the MongoDB
validators that enforce them.

- Database: `aied`
- Collections: `labs`, `lab_files`
- Source of truth: `services/schema.py` — these tables, the `$jsonSchema`
  validators and the index definitions all come from that one file, and
  `tests/test_schema.py` fails if a model gains a field that is not reflected
  there.
- Apply with `python scripts/init_db.py` (`--show` prints without writing).

Types below are BSON types as MongoDB sees them. "Required" means the validator
rejects a document without the field.

---

## Collection: `labs`

One document per lab. Mirrors `LabMaterial` in `models/curriculum.py`.

| Field | Type | Required | Default | Constraints | Notes |
|---|---|---|---|---|---|
| `_id` | objectId | auto | — | — | Mongo's own id; the app never reads it |
| `lab_id` | string | yes | — | — | Unique **within a course**, not globally |
| `course_id` | string | yes | `"csc580"` | — | Part of the real key |
| `title` | string | yes | — | — | e.g. "Linked Lists" |
| `spec_markdown` | string | yes | — | — | The lab handout, markdown |
| `quiz` | array\<object\> | yes | `[]` | items: [quiz question](#embedded-quiz-question) | Regenerated by `request-changes` |
| `rubric` | object | yes | — | [rubric](#embedded-rubric) | Regenerated by `request-changes` |
| `learning_objectives` | array\<string\> | yes | — | — | Drives generation |
| `difficulty` | string | yes | `"intermediate"` | — | Free text today; `basic`/`intermediate`/`challenge` in practice |
| `estimated_duration_min` | int | yes | `90` | ≥ 1 | |
| `material_weight` | string | yes | `"balanced"` | `strict` \| `balanced` \| `expansive` | How closely generation follows the uploaded material |
| `material_content` | string \| null | no | `null` | — | **Derived** — the extracted text of this lab's `material` files, merged in upload order |
| `agent_instructions` | string \| null | no | `null` | — | Free-form instructor text, included in every prompt |
| `approval_status` | string | yes | `"pending"` | `pending` \| `approved` \| `needs_changes` | |
| `approved_by` | string \| null | no | `null` | — | Instructor id |
| `approval_notes` | string \| null | no | `null` | — | |
| `feedback_history` | array\<object\> | yes | `[]` | items: [feedback entry](#embedded-feedback-entry) | Append-only |
| `version` | int | yes | `1` | ≥ 1 | `+1` on every `request-changes` |
| `generated_at` | date | yes | — | — | UTC |
| `last_updated` | date | yes | — | — | UTC |

`additionalProperties: false` — a field not listed here is rejected.

### Indexes

| Keys | Unique | Why |
|---|---|---|
| `course_id: 1, lab_id: 1` | **yes** | The real primary key |
| `course_id: 1, approval_status: 1` | no | "labs awaiting approval" |

> `lab_id` alone was treated as the key before this work, while `course_id`
> existed and defaulted to `csc580`. Two courses each with a `lab4` would have
> overwritten each other.

## Collection: `lab_files`

One document per uploaded file. Mirrors `LabFile` in `models/files.py`.
**The bytes are not here** — they belong to the shared file storage in task 3;
this is metadata plus the text we extracted.

| Field | Type | Required | Default | Constraints | Notes |
|---|---|---|---|---|---|
| `_id` | objectId | auto | — | — | |
| `file_id` | string | yes | — | — | UUID4, generated on upload |
| `lab_id` | string | yes | — | — | → `labs.lab_id` |
| `course_id` | string | yes | `"csc580"` | — | → `labs.course_id` |
| `filename` | string | yes | — | — | As uploaded |
| `content_type` | string | yes | `"application/pdf"` | — | |
| `size_bytes` | int | yes | — | ≥ 0 | Of the original file |
| `kind` | string | yes | `"material"` | `material` \| `instructions` | Only `material` feeds `material_content` |
| `uploaded_by` | string \| null | no | `null` | — | Instructor id when known |
| `uploaded_at` | date | yes | — | — | UTC; the list order |
| `storage_key` | string | yes | — | — | `labs/{course_id}/{lab_id}/{file_id}/{filename}` — pointer into shared file storage |
| `extracted_text` | string | yes | `""` | — | Per file, so one can be removed without re-parsing the rest |
| `char_count` | int | yes | `0` | ≥ 0 | `len(extracted_text)` |

### Indexes

| Keys | Unique | Why |
|---|---|---|
| `file_id: 1` | **yes** | Fetch or delete one file |
| `course_id: 1, lab_id: 1, uploaded_at: -1` | no | List a lab's files |

## Which endpoint writes what

| Endpoint | `labs` | `lab_files` |
|---|---|---|
| `POST /curriculum/generate` | insert or replace; `version=1`, `approval_status="pending"` | — |
| `POST /curriculum/generate-with-material` | insert or replace | insert one per uploaded PDF |
| `GET /curriculum/{lab_id}` | read | — |
| `POST /curriculum/{lab_id}/upload-material` | update `material_content`, `last_updated` | insert one per PDF |
| `POST /curriculum/{lab_id}/upload-instructions` | update `agent_instructions`, `last_updated` | — |
| `GET /curriculum/{lab_id}/files` | read (for `course_id`) | read |
| `DELETE /curriculum/{lab_id}/files/{file_id}` | rebuild `material_content` | delete one |
| `POST /curriculum/{lab_id}/approve` | update `approval_status`, `approved_by`, `approval_notes` | — |
| `POST /curriculum/{lab_id}/request-changes` | replace `quiz` + `rubric`, `version+1`, append `feedback_history`, status → `needs_changes` | — |
| `POST /curriculum/{lab_id}/check-typos` | read | — |
| `GET /curriculum/{lab_id}/export/*.pdf` | read | — |

## Notes for the shared design

1. **Validation level is `moderate`.** New documents and updates to valid
   documents must match; a pre-existing document that does not is left alone
   rather than becoming unreadable. Worth moving to `strict` once the data is
   known to be clean.
2. **`course_id` has no owning collection.** Nothing anywhere defines a course.
   If task 1 or task 3 introduces one, `labs.course_id` and
   `lab_files.course_id` should reference it.
3. **No cross-collection constraint.** MongoDB will not stop a `lab_files`
   document pointing at a `lab_id` that does not exist. The delete endpoint
   checks it in application code; a periodic orphan sweep would be the belt
   and braces.
4. **Version history is not kept.** `request-changes` overwrites `quiz` and
   `rubric` in place; only the feedback text survives, in `feedback_history`.
   Restoring an earlier version would need a `lab_versions` collection holding
   a snapshot per version — cheap to add now, a migration later.
5. **`material_content` is denormalised** — it duplicates text already in
   `lab_files.extracted_text`. That is deliberate: the generation prompts read
   one string, and recomputing it per request would mean a second query on
   every generate. Every write path that touches files rebuilds it.
